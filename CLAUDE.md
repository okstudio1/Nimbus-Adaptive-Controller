# Nimbus Adaptive Controller

Free, open-source modular virtual controller for Windows. Turns mouse/GUI input into vJoy (DirectInput) or ViGEm (Xbox 360 XInput) joystick output. Accessibility-first software alternative to the Xbox Adaptive Controller. Python core plus a Qt Quick (PySide6/QML) UI.

## Key rules
- The QML UI talks to Python only through `ControllerBridge` (src/bridge.py), the single QObject exposed to QML as context property `controller` (config as `config`). QML to Python is `@Slot` methods; Python to QML is Signals. Apply sensitivity curves, deadzones, and smoothing inside the bridge before forwarding to a driver interface, never in QML or the interfaces. Custom-layout widgets send raw geometry (`setStickInput`, `setAxisInput`) and the bridge resolves their shaping settings from the profile by widget id (`_reload_widget_shaping`, `_widget_params`); the formula itself is `shape_magnitude` / `shape_vector` in src/config.py and the dialog's curve preview asks the bridge for its points (`shapeCurve`) rather than copying it.
- Two controller backends must stay behavior-compatible: `VJoyInterface` (8 axes X,Y,Z,RX,RY,RZ,SL0,SL1; 128 buttons) and `ViGEmInterface` (4 axes + 2 triggers; 14 buttons). The bridge selects one per profile `layout_type`. When adding or changing a `set_axis`/`set_button`-style method, mirror it in both and honor each backend's hard limits.
- Custom layouts are a three-way contract: profile JSON `custom_layout.widgets[]`, the rendering in `qml/layouts/CustomLayout.qml` + `qml/components/DraggableWidget.qml`, and the bridge mapping. Adding a widget `type` or field means updating all three (plus `profiles/adaptive_platform_2.json` if it is a default).
- Windows/driver-specific modules (vigem_interface, window_utils, borderless, mouse_hider) are imported under try/except into `*_AVAILABLE` flags. Keep that graceful-degradation pattern so the app still starts with the driver missing or on non-Windows. `src/mouse_isolation_win.py` is imported the same way (Windows only, `MOUSE_ISOLATION_AVAILABLE` is True only when the filter driver's device exists) and drives Full Game Mode's mouse isolation with the cursor relay; its Linux twin on the `linux-uinput-support` branch uses the same class API and the same bridge names, so reconcile rather than duplicate when that branch merges.
- `driver/nimbus_moufilter/nimbus_moufilter_ioctl.h` and the constants at the top of `src/mouse_isolation_win.py` are one contract (device name, IOCTL codes, status struct, `MOUSE_INPUT_DATA` packing). Change them together and bump `NIMBUS_MOUFILTER_INTERFACE_VERSION`. The Windows and Linux `MouseIsolation` classes must keep the same constructor, `start`/`stop`, and callback signatures so `bridge.py` can use either once the Linux branch merges.
- Telemetry stays opt-in only, no PII, hashed identifiers, local-first (src/telemetry.py, src/cloud_client.py, keyring for secrets). Do not add default-on collection or log identifying data.
- `controller_config.json` is generated per-machine and is gitignored, so never commit it. Bundled default profiles live in `profiles/`; user profiles live in `%APPDATA%/ProjectNimbus/profiles/`. The internal app/data-dir name is `ProjectNimbus` (config.py `APP_NAME`), so do not rename it.
- Do not add features to non-primary shells: `src/legacy/` (pygame) and `src/qt_main.py` + `src/qt_widgets.py` (Qt Widgets) are reference-only and not at feature parity. The QML app is the one true UI.

## Stack & layout
- Python 3.8+ with PySide6 (Qt Quick/QML), pyvjoy, numpy, PyInstaller. Xbox 360 output reaches ViGEmBus through `src/padbus_client.py`, a pure-ctypes client for the bus protocol (no `vgamepad`, no client DLL); its `X360Pad` keeps vgamepad's method names on purpose, `BUS_INTERFACES` lists the device interface GUIDs to probe so a Nimbus-owned bus is one more entry, and `PADBUS_AVAILABLE` is True only when a bus device is present. The plan it comes from is `docs/vision/PAD_BUS_FORK_PLAN.md`.
- `src/` Python core: bridge, config, vjoy_interface, vigem_interface, borderless, window_utils, mouse_hider, mouse_isolation_win, telemetry, cloud_client.
- `qml/` UI: `Main.qml`, `layouts/`, `components/`.
- `profiles/` bundled default profile JSON. `build_tools/` PyInstaller packaging. `tests/` vJoy hardware diagnostics and the Windows input probes. `docs/` architecture and dev notes.
- `driver/` the Nimbus Mouse Filter (KMDF, Windows only). Built with `driver\build.ps1`, which needs Visual Studio 2022 with the WDK component and WDK 10.0.26100; it is not part of `run.py` or the installer yet. Loading it needs test signing (see `driver/README.md`). Never install or load a kernel driver on someone's machine without asking. Once the filter is registered as a mouse-class upper filter it is mandatory: anything that stops Code Integrity accepting the test-signed `.sys` (a Windows update, `bcdedit /set testsigning off`, Secure Boot back on) means Windows starts **no mouse at all**, and a working TeamViewer cursor hides it because `SendInput` never touches `mouclass`. So never turn test signing off while it is installed; use `driver\disable-testsigning.ps1`, which detaches first. `driver\check-mouse-filter.ps1` (read-only, no elevation) says whether the mouse would survive the next reboot, and elevated `driver\recover-mouse.ps1` gets it back with no reboot. This happened on 2026-09-07; see `driver/README.md` and section 5 item 12 of the plan doc.

## Build, run, test
- Run: `python run.py` (auto-creates `venv/`, installs requirements, launches `src.qt_qml_app`). Modules run as packages, so keep `src.`-qualified or relative imports.
- Deps: `pip install -r requirements.txt`.
- Package: follow `build_tools/BUILD_EXECUTABLE.md` (PyInstaller via `build_tools/Nimbus-Adaptive-Controller.spec`).
- Tests: `python tests/run_fast_tests.py` runs the fast, hardware-free suite (the ten `tests/test_*.py` files, seconds, no driver), and it is what CI runs (`.github/workflows/fast-tests.yml`, `windows-latest`, `QT_QPA_PLATFORM=offscreen`, `requirements.txt` without `pyinstaller`). The files import the app as `src.<module>`, so run one on its own **as a module from the repo root** (`python -m tests.test_bridge_services`), never by path. `test_vjoy.py` and `test_dialog.py` match the pattern and are skipped by name (a vJoy driver diagnostic and an interactive pygame script for the legacy shell); the `probe_*_windows.py` files are hardware probes a person runs. pytest is not a dependency. `tests/test_frame_motion.py` covers `tests/frame_motion.py`, the frame motion measurement the game harness uses, with synthetic pictures. The plan behind all of this, and what it found, is `docs/vision/TESTING_STRATEGY.md`.
- Bus client changes: run `tests/test_padbus_client.py` (pure Python, the protocol constants and packing) and `tests/probe_padbus_windows.py` (the real ViGEmBus, about 30 s: plug, XInput read-back, handle-death unplug, replug storm, timing) after any change to `src/padbus_client.py`, then the shaping probe below, since its expected values only hold if the client's float conversion is unchanged.
- Stick shaping changes: run `tests/test_stick_shaping.py` (pure Python, no hardware) and `tests/probe_stick_shaping_windows.py` (the real app, needs ViGEmBus, about 40 s, safe over TeamViewer) after any change to `shape_*` in src/config.py, `setStickInput` / `setAxisInput` in the bridge, the stick paths in `DraggableWidget.qml`, or the widget config dialog in `CustomLayout.qml`; the probe's expected values come from the bridge's own resolved parameters. `tests/probe_game_deadzone_windows.py` measures a game's real stick deadzone and must be started before the game launches. The plan and the results log are in `docs/vision/AIM_ASSISTANCE.md`, sections 12 and 14.
- Real-game tests: `tests/probe_game_harness_windows.py --game left4dead2 --actuator pad` (calibrates the game through its console, about four minutes, unattended, launches and quits the game itself; `--write-calibration` refreshes `src/spectator/calibrations/left4dead2.json`) and `--actuator nimbus` (the real app end to end, then the Spectator+ primitives). Recipes are `tests/games/*.json` (`halflife2` is the second Source game; `eldenring`, `powerwashsimulator` and `halowars` use the frame-differencing oracle and a `ready_sequence`, PowerWash's menus need the `pointer` step because A there clicks a virtual pointer the left stick moves rather than a highlight, and Halo Wars is the RTS whose sticks drive a camera, whose menus need buttons the bundled profile draws no widget for, and whose timed sequence cannot use `press_until_control` because its title screen animates); the machinery is `tests/game_harness.py`; the plan and the results log are `docs/vision/GAME_TEST_HARNESS.md`. `arma3` (BattlEye, launched by its `exe` key through `arma3battleye.exe`) and `arma3_nobe` (the control) use the `arma3` oracle: a generated mission whose script publishes the pose through the clipboard and takes reset and `NIMBUS_EXEC` script commands back from it, so a copy or paste during a run breaks a read, the pad must be enabled in the player's profile (the oracle does it, behind a backup), the window is applied at readiness only, and nothing presses Start (it freezes the mission's script). Run one at a time so each session's pad is player one. Rerun both after any change to `src/spectator/`, `ControllerBridge.get_spectator`, or the calibration. **Leave the mouse and keyboard alone while one runs**: these games read the mouse for look and the harness foregrounds the game window for each step, so a hand on the mouse turns the camera inside the measurement and nothing can tell it from the pad. Unattended means it needs no help, not that the machine is free. For the same reason the runner never asserts the foreground between the two pose reads of a delta (`front()` warps the cursor). Half-Life 2 needs `--cal-mags 0.4,0.6` when writing its calibration, because its full-deflection turn folds past 180 degrees between pose samples. Recipes may also carry `window` (the harness sizes the game with `src/borderless.py` and records whether it took), `motion` (`{"kind": "rotate"}` for a camera that swings rather than pans, Halo Wars), `reset_buttons` (a reset for a game with no console, checked against a reference frame) and `expect` (bands on the rates a check measured last time, so a run fails when the game's answer changes; `--write-expect` fills them from a good run). Frame verdicts come from `tests/frame_motion.py` (phase correlation and a change grid, never a bare changed-sample count) with thresholds from `--idle-samples` idle seconds.
- Driver changes: run `tests/probe_mouse_filter_windows.py` and `tests/probe_mouse_filter_stress_windows.py` (the battle test, about four minutes, unattended, needs the filter installed) after any change to `driver/` or `src/mouse_isolation_win.py`, and WDK Code Analysis plus CodeQL before a driver commit. The commands and the results log live in `docs/vision/WINDOWS_MOUSE_FILTER_PLAN.md`, section 5.

## Conventions
- PEP 8, type hints, and numpy-style docstrings on public classes and methods (match src/bridge.py). No linter or formatter is configured, so keep the existing style and avoid ruff/black reformatting churn.
- Keep vJoy axis names uppercase (X, Y, Z, RX, RY, RZ, SL0, SL1); button IDs are 1-based.

## When to ask
- Changing the profile / `custom_layout` JSON schema or the `controller_config.json` shape (needs migration plus all three layers updated).
- Changing telemetry scope, cloud endpoints, or credential handling.
- Touching a driver interface in a way that could inject unintended input, or changing failsafe / rate-limit behavior.
